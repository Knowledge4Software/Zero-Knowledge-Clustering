# اصلاح بودجهٔ استورج بر اساس اندازه‌گیری

پیشنهاد قبلیِ۵۰۰GB یک حاشیهٔ راحتیِ بدون اندازه‌گیری بود و برای کمپین متعادل الزام نیست. پیشنهاد اصلاح‌شده **۵۰GB برای راحتی، هدف مینیمال۳۰GB با مدیریت فعال فضا** است. کفایت۲۰GB یا peak کل کمپین هنوز اندازه‌گیری نشده؛ آن‌ها را تضمین نمی‌کنیم.

اندازهٔ فعلی فایل‌ها، شامل کپی‌های موجود کلیدها و cacheهای proof:

| مورد موجود | مجموع اندازهٔ فایل‌ها |
|---|---:|
| Fashion N32، کل پوشهٔ مقایسهٔ چهار روش |۲٫۰۲۰GiB|
| متن N32، کل پوشهٔ مقایسهٔ چهار روش و fallbackهایش |۱٫۵۳۱GiB|
| Fashion N128، پوشهٔ مقایسهٔ فعلی با PCA ناقص |۲٫۳۹۵GiB|
| کمپین هزینه‌آگاه دور اول، شامل دو داده و چند کپی setup |۱٫۶۰۴GiB|
| دور دوم متنِ مستقیم Full |۰٫۲۰۰GiB|
| cache دادهٔ فعلی، حتی شامل منابع نامرتبط با این کمپین |۰٫۱۹۰GiB|
| پوشهٔ دادهٔ review فعلی، شامل منابع اضافی |۰٫۰۹۲GiB|

بخش غالب، proving keyها و constraint systemهاست؛ نه خود داده یا proofهای نهایی. نمونه: کلید Full تصویر حدود۲۶۸MiB و کلید Halo2 تصویر N128 حدود۶۶۴MiB است. تعداد بیشتر query با مدل/مدار ثابت، به معنی ساخت کلید تازه برای هر query نیست. تغییر fit/basis/model ممکن است کلید تازه بخواهد و باید فضای آن حساب شود.

محیط WSL فعلی با `du -sh` حدود۱٫۲GiB برای محیط جداگانهٔ Python/Rust/Cargo و۳۱۲MiB برای پوشهٔ build هدف ZKML نشان داد. این اندازه‌ها مصرف فعلی همین محیط‌اند؛ اندازهٔ OS سرور، همهٔ dependencyهای احتمالی یا نیاز build بزرگ‌تر را تضمین نمی‌کنند. مسیر پیش‌فرض Go cache در WSL فعلی موجود نبود؛ از این نبودن، نیاز صفرِ build Go نتیجه نمی‌گیریم.

برای هدف۳۰GB:

- فقط کد و دادهٔ لازم منتقل شود؛ کل تاریخچهٔ پروژه و ران‌های قبلی منتقل نشوند.
- تا حد سازگاری CPU و نسخه‌ها، binaryهای Linux آماده شوند تا build/cache اضافیِ غیرلازم روی سرور کم شود. نسخهٔ اجرا و source برای بازتولید باقی بمانند.
- کلیدهای immutable یکسان بین query chunkها و تکرارهای warm، تک‌نسخه باشند؛ مدل/کلید متفاوت به‌اشتباه یکی فرض نشود. هزینهٔ setup در حساب زمان همچنان شفاف بماند.
- تعداد پروفایل‌های فعال محدود شود. پس از اتمام و بررسی یک گروه، خروجی‌ها به لپ‌تاپ منتقل و hash آن‌ها تطبیق داده شود؛ فقط آن‌وقت cacheهای قابل بازسازی طبق سیاست مشخص قابل بازنشستگی‌اند.
- proofها، verification keyها، pinها، approved task، manifest، رسیدها و نتایج معتبر حفظ شوند. بازسازی دوبارهٔ cache/کلید هزینه دارد؛ حذف زودهنگامِ کلیدهای مورد نیاز warm مجاز نیست.

**گارد فعلی لپ‌تاپ۱۲GiB فضای آزاد می‌خواهد.** بنابراین مخصوصاً روی۲۰GB نمی‌توان همین تنظیمات را بدون طراحی دوبارهٔ ظرفیت استفاده کرد. گارد تاریخی تغییر نکرده است. برای سرور کوچک، اندازهٔ بیشترین فایل موقت/کلید و فضای لازمِ هر job در canary بررسی و reserve جدا تعریف شود؛ کم‌کردن صرفِ عدد reserve تضمین کفایت نیست.

نتیجهٔ عملی:۳۰GB می‌تواند هدف اجرای کم‌حجم باشد، با نصب سبک و انتقال خروجی.۵۰GB حاشیهٔ مناسب‌تری دارد. برای این طرح هزینهٔ۵۰۰GB لازم نیست. هیچ فایل آزمایش، کلید یا cache در این بررسی حذف نشده است.
